# Technical Debt

Confirmed items, as of the Core MVP build (2026-08-14) — logged honestly, not hidden.

- **Update (review follow-up)**: convert-lead race now guarded by a conditional `updateMany`; auth rate limiting, helmet and startup env validation added; a basic automated test suite exists. Remaining: JWT in `localStorage`, DB-backed integration tests, kanban 100-row cap, no call-log UI, `FOLLOWUP_UPCOMING`/`TASK_OVERDUE` notifications have no scheduler, register still reveals whether an email exists (409).
- **Convert-lead race condition** (original note; mitigated as above): `POST /leads/:id/convert`'s idempotency check (lead not already `CONVERTED`) runs inside a single DB transaction, but two near-simultaneous requests could theoretically both pass the check under Postgres's default READ COMMITTED isolation before either commits. Primary mitigation is the frontend disabling the Convert button immediately on click (`ConvertLeadButton.jsx`). Acceptable for MVP; a stricter fix (e.g. `SELECT ... FOR UPDATE` or a unique partial index) would close the gap if this ever became a real issue in practice. Not reproduced — this is a theoretical gap identified during design, not an observed bug.
- **Automated tests (partly resolved)**: a server suite now exists (see `TESTING.md`); client tests and DB tests in CI are still missing. Original note: explicitly deferred (see `FUTURE_FEATURES.md`). All verification for this build was manual (see `TESTING.md`). Highest-risk untested-by-automation area: the RBAC/ownership-scoping logic in `utils/ownership.js` — a regression there means one sales rep seeing another's data. Manually verified working for this build (see `TESTING.md`), but nothing guards against a future regression.
- **JWT in `localStorage`**: readable by any JS running on the page, so an XSS vulnerability elsewhere in the app would allow token theft. Acceptable for local-dev MVP; would reconsider (httpOnly cookie + CSRF token) before any production deployment.
- **Kanban board list caps at 100 opportunities**: `PipelinePage` requests `limit: 100` (the API's max page size); a business with more than 100 open deals would see the board silently truncate rather than paginate. Not a concern at MVP data volumes; would need real pagination or virtualization in the kanban board if it becomes one.
- **`OpportunityForm`'s customer picker doesn't scale**: it's a plain `<select>` populated from the first 100 customers, not a searchable autocomplete. Fine for MVP customer counts; would need a proper combobox component if the customer list grows large. **Resolved 2026-08-22**: replaced with the new `Combobox` common component (client-side search over the same up-to-100 fetch) in both `OpportunityForm` and `LinkPicker`'s record picker — see `DECISIONS.md`.
- **Auth rate limiting (resolved, with caveat)**: now in place (in-memory, per instance; needs a shared store for multi-instance). Original note: `POST /auth/login` and `/auth/register` have no brute-force protection. Acceptable for local-dev MVP; would need this before any internet-facing deployment.
- **Bundle not code-split**: `vite build` warns the JS bundle is >500kB (mainly Recharts + react-router + axios + the full app in one chunk). Not a functional problem at this scale; route-based `React.lazy` code-splitting would be the fix if load time ever becomes a concern. **Resolved 2026-08-22**: routes now lazy-load per page via `React.lazy`/`Suspense` in `AppRoutes.jsx` — see `DECISIONS.md`.
